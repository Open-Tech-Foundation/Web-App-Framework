# Server

API routes, middleware and loaders are standard server modules. A fullstack app
provides a **server entry** that composes them and hosts the request pipeline.
The retired CLI no longer supplies that server automatically.

## Native API server

This minimal entry mounts one API module on ES-Runtime:

```js server.js
import { serve } from "runtime:http";
import { env } from "runtime:process";
import { createApiHandler } from "@opentf/web/server";
import * as hello from "./app/api/hello/route.js";

const api = createApiHandler({ "/app/api/hello/route.js": hello });
serve({ hostname: "127.0.0.1", port: Number(env.PORT || 8080) }, async (request) =>
  await api(request) || new Response("Not found", { status: 404 })
);
```

Add a server target alongside the browser target in `esdev.json`:

```json
"server": { "entry": "server.js", "out": "dist/server.js", "platform": "server" }
```

Use the default OTF plugin with `mode: "ssr"` when the server imports renderable
components. Server modules compile to string renderers, while browser release
modules compile for hydration.

```bash
esdev build --minify
esdev dist/server.js
```

This example hosts APIs only. Static assets, SSR and additional routes belong in
the app's server entry. The native plugin integration tests verify compiled server
rendering, real HTTP API requests, middleware and loader data endpoints.

## Compose a full pipeline

Use `createMiddleware` around the request pipeline, then try API dispatch, loader
data endpoints, static assets and page rendering. `createLoaderRegistry` supplies
`match`, `load` and `handle`; `renderRoute` composes registered pages/layouts.

Thread the live request, query and middleware locals into loaders. Include serialized
route data and island props in server HTML so client navigation and hydration resume
with the same data. Request rendering uses shared route/collector state; the server
entry must account for overlapping requests rather than assuming isolated renderers.

<Callout type="info" title="Starter work remains upstream">
  The installed esdev 0.14 fullstack template still refers to the retired server
  command. Its replacement needs a server entry, request pipeline and native build/dev
  config. An updated compiler plugin alone does not supply those files.
</Callout>

## Other runtimes

For Fetch-native platforms, `createFetchHandler` composes dispatch and middleware
with a fallback for assets or SSR. When your build script emits `dist/server/api.js`,
see [Fetch handler](/docs/deployment/fetch-handler) for adapter wiring.

Node applications import `toNodeListener` from `@opentf/web/server/adapters/node`.
Keep runtime-specific imports in the server entry, not in client components.

## Environment and server-only imports

On ES-Runtime, read variables from `runtime:process`'s `env`. Other hosts expose
variables through their own environment API, and Fetch platforms can pass bindings
as `context.env`/`context.ctx`. Configure environment loading for your chosen host;
the retired CLI's automatic Bun `.env` loading is not part of esdev integration.

Keep database clients and secrets in `loader.*`, `route.*`, `_middleware.*` and
server entries. The compiler does not provide a guarantee that arbitrary imports
placed in client components stay server-only.

See [API Routes](/docs/routing/api-routes), [Middleware](/docs/routing/middleware)
and [Data Fetching](/docs/data-fetching).
