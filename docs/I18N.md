# Internationalization (i18n)

> **Status:** Phase 1 (runtime) — implemented. Phase 2 (compiler) — designed here,
> not yet built. This document is the authoritative design for i18n; it conforms to
> [`ARCHITECTURE.md`](../ARCHITECTURE.md) (one source, many IRs, many targets) and
> the backend-parity rule (every rendering backend must agree).

---

## 1. Goals

Make an app adapt to a language/region with no code changes:

- **Message translation** with full **ICU MessageFormat** (interpolation, plurals,
  select, number/date skeletons).
- **Locale routing** by URL path prefix.
- **Locale-aware formatting** of numbers, currency, dates, and relative time.
- **SEO**: per-locale `<html lang>` and `hreflang` alternate links.
- Correct rendering across **all backends** — CSR, SSG, SSR, Hydrate — from one source.

Non-goals (this design): in-place (no-reload) locale switching, and
domain/subdomain routing strategies. See §8.

---

## 2. Routing model — `prefix_except_default`

The active locale lives in the **URL path**. The default locale is served at the
bare path; every other locale is prefixed:

```
/about        → default locale (e.g. en)
/fr/about     → fr
/ja/about     → ja
```

**Switching locale is always a URL-based fetch** (a navigation), never an in-place
toggle. This single constraint is the keystone of the whole design: because each
URL is exactly one locale, **the locale is a per-render constant**. The reactive
`router.locale` signal only changes on navigation — which re-renders the page
anyway — so static translated text never needs to re-translate in place.

One **locale-agnostic route table** serves all locales. The router strips a leading
locale segment (when it is a configured non-default locale), records it as
`router.locale`, and matches the remainder against the normal routes. `<Link>` and
programmatic navigation re-attach the current locale prefix via `localizePath()`.

Locale detection (SSR): a request with no locale prefix whose `Accept-Language` /
cookie prefers a **non-default** locale is redirected to the prefixed URL. The
default locale serves bare with no redirect.

## 3. The hybrid compile/runtime model

A translated string is just an **expression** — and the View IR already splits
every view into **static structure** (pre-rendered, adopted marker-free on hydrate)
and **Dynamic holes** (wired through the Reactivity IR; ARCHITECTURE.md §4.2–4.3).
i18n slots into that exact seam. There is **one `t()` API**; the compiler decides
the *delivery* per call-site:

| Tier | Condition | Delivery | Build-time wins |
|---|---|---|---|
| **1 — static inline** | literal key, no runtime params | string baked into the per-locale HTML | extracted, validated, **tree-shaken** |
| **2 — reactive hole** | literal key, interpolates a runtime signal | Dynamic text hole calling `t()` at runtime | key validated + tree-shaken |
| **3 — dynamic key** | `t(expr)` — key unknown at build | pure runtime lookup | dev marks keys to retain |

Because locale is fixed per URL (§2), Tier 1 inlining is always safe — the compiler
never has to keep multiple locales resident. **Phase 1 (this release) implements the
runtime, so every call-site behaves as Tier 2/3.** **Phase 2** adds the `otfwc` pass
that *promotes* eligible call-sites to Tier 1 — an identical app-facing API, so it is
a non-breaking optimization, not a rewrite.

---

## 4. Backend parity

| Backend | Static message (Tier 1, Phase 2) | Dynamic message (Tier 2/3, Phase 1) |
|---|---|---|
| **CSR** | rendered from the loaded catalog on mount | `t()` reads `router.locale` + catalog |
| **SSG** | inlined into `dist/<locale>/route/index.html` | rendered into HTML at build (locale pinned) |
| **SSR** | inlined per request | rendered per request (locale from URL) |
| **Hydrate** | server string adopted, no re-render | server pins locale → client reads same locale from URL → **no mismatch** |

The hydrate no-mismatch guarantee falls directly out of §2: the client derives the
exact locale the server used from the URL, so adopted text is identical.

## 5. Public API (Phase 1)

### Core `@opentf/web` (routing)

```js
import { router, localizePath } from "@opentf/web";

router.locale                 // reactive — the active locale ("en", "fr", …)
localizePath("/about", "fr")  // "/fr/about"  (bare for the default locale)
```

`mountApp({ pages, target, i18n })` accepts `i18n: { locales, defaultLocale }`.
`<Link href="/about">` automatically stays in the active locale.

### `@opentf/web-i18n` (messages + formatting)

```js
import { createI18n, t, fmt } from "@opentf/web-i18n";

createI18n({
  locales: ["en", "fr", "ja"],
  defaultLocale: "en",
  // eager:
  messages: { en: { greeting: "Hello, {name}" }, fr: { greeting: "Bonjour, {name}" } },
  // or lazy / code-split per locale:
  // load: (locale) => import(`./messages/${locale}.json`),
});

t("greeting", { name: "Ada" });                  // reactive on router.locale
t("cart.items", { count });                       // ICU: "{count, plural, one {# item} other {# items}}"

fmt.number(1234.5);                               // locale-grouped
fmt.currency(189, "USD");                         // "$189.00" / "189,00 $US"
fmt.date(new Date(), { dateStyle: "long" });
fmt.relativeTime(-3, "day");
```

```jsx
import { T } from "@opentf/web-i18n";
<T id="greeting" values={{ name }} />            // inline JSX form of t()
```

`t()` and `fmt.*` read the active locale from core's `router.locale` signal, so they
are reactive: a navigation that changes the locale re-renders them fine-grained.
Lookups fall back `activeLocale → defaultLocale → raw key`. ICU is provided by
[`intl-messageformat`](https://formatjs.io/docs/intl-messageformat/); the framework
owns the catalog, loading, reactive binding, and `Intl` formatter memoization.

### Catalog convention

Per-locale message maps keyed by message id, eager (`messages`) or lazy (`load`,
code-split). Recommended layout: `app/messages/<locale>.json`.

## 6. Toolchain

- **`otfw.config`** — `i18n: { locales, defaultLocale, routing: "prefix_except_default" }`.
- **App entry** — the generated `mountApp({ … })` is threaded with the `i18n` config.
- **SSG** — each route is pre-rendered **once per locale**: default at
  `dist/<route>/index.html`, others at `dist/<locale>/<route>/index.html`, with the
  locale pinned via `setRouteState({ locale })` before each render, and per-page
  `<html lang>` + `hreflang` alternates emitted.
- **SSR (`otfw serve`)** — parse the locale prefix from the request; detect +
  redirect bare → prefixed for non-default locales; pass the locale to `renderRoute`.

## 7. Phase 2 — compiler design (not built)

A `otfwc` extraction pass turns Tier-2 call-sites into Tier-1 where provable:

1. **Extract** — scan `t("literal", …)` and `<T id="…">`; collect message ids per
   module into a **Message IR** (a focused IR, or a Metadata IR extension; ARCHITECTURE.md §4).
2. **Validate** — every id exists in the default-locale catalog; ICU arg names match
   the call-site `values`. Errors at build, with source spans (§5.4).
3. **Tree-shake** — drop catalog entries no call-site references (Tier-3 keys are
   retained via an explicit `keep` hint / registry, since their key is dynamic).
4. **Inline** — for literal-key, signal-free call-sites, fold the resolved string
   into the per-locale SSG/SSR HTML (Tier 1); leave signal-interpolating call-sites
   as Tier-2 reactive holes.

The app source does not change between phases — `t("…")` stays `t("…")`; only the
generated code gets faster and smaller.

## 8. Open / deferred

- In-place locale switching without navigation (excluded by the §2 decision).
- Domain / subdomain routing strategies.
- Translator tooling (catalog extraction CLI, missing-key reports) — rides on the
  Phase 2 Message IR.
- Pluralization-aware catalog authoring helpers.
